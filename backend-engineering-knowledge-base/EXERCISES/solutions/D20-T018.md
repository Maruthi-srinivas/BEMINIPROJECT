# Solutions — D20-T018

## Exercise 1

Property-based testing states a property that must hold for many generated inputs, instead of one example. A generator builds values. The framework shrinks a failing value to a smaller one. Properties include round-trip, idempotence, and invariants. A property that is too weak, such as 'does not throw,' proves little. You still keep a few examples for the cases humans must read.

The failure enters when a step is skipped or repeated without an invariant: a property that encodes the same bug as the implementation, so both are wrong together.

Mark that step on the diagram. If you cannot point to a step, the explanation is still a definition, not a mechanism.

## Exercise 2

The assertion should fail when a property that encodes the same bug as the implementation, so both are wrong together.

Watch failures found by generation that example tests missed. A test that only checks a 200 status does not lock the invariant.

## Exercise 3

Choose Property-based testing when the correct behavior is a rule over a large input space.

Avoid it when you assert the implementation against a copy of itself.

A good answer names the metric that would change your mind: failures found by generation that example tests missed.
