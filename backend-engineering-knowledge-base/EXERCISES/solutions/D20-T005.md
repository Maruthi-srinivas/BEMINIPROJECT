# Solutions — D20-T005

## Exercise 1

An end-to-end test runs a user journey through the deployed system, or a close stand-in, including the UI or the public API and the real path to the database. It catches wiring mistakes. It is slow and flake-prone, so a few journeys are enough. It does not replace the tests that pinpoint a function. Setup and data must be isolated.

The failure enters when a step is skipped or repeated without an invariant: a large end-to-end suite that fails on shared data or timing and gets ignored.

Mark that step on the diagram. If you cannot point to a step, the explanation is still a definition, not a mechanism.

## Exercise 2

The assertion should fail when a large end-to-end suite that fails on shared data or timing and gets ignored.

Watch flake rate and the number of defects that only the journey test could see. A test that only checks a 200 status does not lock the invariant.

## Exercise 3

Choose End-to-end testing when you need confidence the wired system completes a journey.

Avoid it when you try to cover every branch this way.

A good answer names the metric that would change your mind: flake rate and the number of defects that only the journey test could see.
