# Solutions — D13-T009

## Exercise 1

Lock-free programming updates shared data with atomic primitives such as compare-and-swap instead of a mutex. A thread that fails a CAS retries. Progress for the system continues even if one thread stalls, which is the usual lock-free guarantee. It is not wait-free, which would bound each thread's own steps. ABA, memory ordering, and a retry loop that livelocks under contention are the real bugs.

The failure enters when a step is skipped or repeated without an invariant: an ABA bug or a CAS loop saturating a core while a mutex would have queued quietly.

Mark that step on the diagram. If you cannot point to a step, the explanation is still a definition, not a mechanism.

## Exercise 3

Choose Lock-free programming basics when the update is one word and the critical section is tiny.

Avoid it when the invariant spans multiple words or the contention is high enough that a queueing lock is kinder.

A good answer names the metric that would change your mind: CAS failure rate and the number of retries before success.
