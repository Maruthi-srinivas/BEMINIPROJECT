# Solutions — D20-T010

## Exercise 1

Acceptance testing checks a behavior against a requirement a stakeholder would recognize. It is written in the language of the outcome, not the language of a private class. It can be automated. It answers 'did we build the thing we agreed,' not 'did this function return 4.' The example should be readable by the person who asked for the feature.

The failure enters when a step is skipped or repeated without an invariant: a test named acceptance that only asserts a mock was called.

Mark that step on the diagram. If you cannot point to a step, the explanation is still a definition, not a mechanism.

## Exercise 2

The assertion should fail when a test named acceptance that only asserts a mock was called.

Watch requirements that shipped without an example anyone can read. A test that only checks a 200 status does not lock the invariant.

## Exercise 3

Choose Acceptance testing when a requirement can be phrased as a user-visible outcome.

Avoid it when you mock the entire application and still call it acceptance.

A good answer names the metric that would change your mind: requirements that shipped without an example anyone can read.
