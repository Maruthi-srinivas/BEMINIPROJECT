# Solutions — D20-T002

## Exercise 1

An integration test runs a slice of the system with real collaborators you chose not to fake, such as a database or a queue, and checks a behavior across that boundary. It is slower than a unit test and catches SQL, migrations, and serialization bugs. It should still be deterministic. It does not need the whole production mesh.

The failure enters when a step is skipped or repeated without an invariant: a test that shares a database row with another test and fails only in CI.

Mark that step on the diagram. If you cannot point to a step, the explanation is still a definition, not a mechanism.

The assertion should fail when a test that shares a database row with another test and fails only in CI.

Watch flake rate and time spent in the integration stage. A test that only checks a 200 status does not lock the invariant.

## Exercise 3

Choose Integration testing when the bug you fear lives in the boundary between your code and a real dependency.

Avoid it when you boot the entire platform for a one-line calculation.

A good answer names the metric that would change your mind: flake rate and time spent in the integration stage.
