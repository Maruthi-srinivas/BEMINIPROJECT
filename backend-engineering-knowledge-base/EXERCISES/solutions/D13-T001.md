## Exercise 1

```python
import multiprocessing as mp


def worker(chunk, q):
    q.put(sum(chunk))


def parallel_sum(n: int, workers: int = 2) -> int:
    chunks = [range(i, n, workers) for i in range(workers)]
    q: mp.Queue = mp.Queue()
    procs = [mp.Process(target=worker, args=(list(c), q)) for c in chunks]
    for p in procs:
        p.start()
    total = sum(q.get() for _ in procs)
    for p in procs:
        p.join()
    return total


if __name__ == "__main__":
    assert parallel_sum(10_000) == sum(range(10_000))
```

Workers run in separate processes; the queue returns partial sums. Chunking by stride is simple; production code might split by size.

## Exercise 2

The bug is a data race: `counter += 1` is read-modify-write without synchronization, so updates are lost. Fix with `threading.Lock` around the increment, or use `itertools` aggregation per thread then sum, or `multiprocessing.Value` with a lock for cross-process cases.

## Exercise 3

Eight processes isolate memory and bypass the GIL for any stray CPU in Python; they duplicate baseline memory and connection pools unless tuned. One process with 64 threads shares pools and suits I/O wait, but mis-sized pools can exhaust DB connections or file descriptors. Measure p99 latency, active DB connections, process memory, CPU utilization per core, and error rate under peak RPS before choosing.
